# selmo. 技術設計方針

## 基本方針

selmo.はSupabase、Vercel、OpenAI、Google Cloudなどのマネージドサービスを活用する。ただし、プロダクトの中核データと業務ロジックを特定ベンダーの固有機能へ閉じ込めない。

> マネージドサービスは開発・運用を速める実装手段として利用し、selmo.そのものの所有権と移行可能性は自社で維持する。

完全なベンダー非依存を目的にはしない。交換可能性が事業継続、販売先、コスト、性能、法令対応に影響する箇所へ、明確な境界を設ける。

## 自社で管理する資産

次の情報は、利用サービスにかかわらず自社で定義・移行・復元できる状態を維持する。

- 組織、部門、ユーザー、ロールのデータモデル
- 顧客、営業予定、訪問・商談履歴
- 文字起こし、商談要約、分析結果、評価基準
- ロープレ課題、シナリオ、採点結果
- ナレッジと検索用メタデータ
- データベーススキーマとマイグレーション履歴
- AIプロンプト、構造化出力スキーマ、評価ロジック
- CSV等によるインポート・エクスポート仕様

## 採用する境界

```text
UI / Server Actions
        ↓
Application Services（業務処理）
        ↓
Repository / Provider Interfaces
        ↓
Supabase・OpenAI・GCS等の実装
        ↓
PostgreSQL・オブジェクトストレージ・AIモデル
```

画面コンポーネントへデータ取得、権限判断、AIプロンプトを直接書き込まない。業務処理をApplication Servicesへ置き、外部サービス固有の処理をAdapterまたはProvider実装へ閉じ込める。

## データベース

- PostgreSQLを正とし、標準SQL、外部キー、制約、インデックスを優先する。
- 全スキーマ変更を`supabase/migrations`のSQLとしてGit管理する。
- Supabase管理画面だけでスキーマを変更しない。緊急変更時も同一内容のマイグレーションを残す。
- 全業務テーブルに`organization_id`を持たせることを原則とし、別会社のデータ混在を防ぐ。
- ベンダー固有の拡張は、代替手段と移行方法が説明できる場合に限定する。
- 定期的に論理バックアップを取得できる設計にし、標準PostgreSQLへ復元可能にする。
- 顧客、営業履歴、分析結果は標準形式でエクスポート可能にする。

### Supabase固有部分

認証はFirebase Authenticationを利用し、SupabaseはPostgreSQLホスティングとして利用する。依存を次の範囲へ限定する。

- `src/lib/firebase`：Firebase Client/Admin初期化
- `src/lib/auth`：サーバーセッション、現在ユーザー、認可Context
- `src/lib/supabase/admin.ts`：サーバー限定DB接続

将来Firebase Auth、Auth0等へ変更する場合は、認証Adapterと権限判定関数を交換対象とし、業務テーブルを作り直さない。

## 認証と認可

- 認証は「本人確認」、認可は「閲覧・操作可能範囲」として分離する。
- ロール名だけで判定せず、組織、所属部門、担当部門、対象データの所有者を使って判定する。
- 中核のアクセス制御はPostgreSQL RLSでも強制し、UIの非表示だけに依存しない。
- Server ActionsとAPIは、クライアントから渡されたユーザーIDやロールを信用しない。
- Secret keyや管理用DB接続はブラウザへ渡さない。
- 公開サインアップは設けず、管理された招待・発行フローを使用する。

## ファイル・音声

- DBにはファイル本体ではなく、保存先、所有組織、メタデータ、処理状態を保存する。
- Storage Providerインターフェースを設け、Supabase Storage、GCS、S3を交換可能にする。
- 署名付きURLの発行や権限確認をProvider層へ閉じ込める。
- selmo.は文字起こし結果以降の分析を主軸とし、録音・文字起こしはvoimo.とのAPIまたはファイル連携として扱う。

## AI

- モデル名を画面や業務ロジックへ直接埋め込まない。
- AI Provider層を通じて、モデル、タイムアウト、リトライ、コスト上限を設定する。
- プロンプトと構造化出力スキーマをバージョン管理する。
- 各生成結果に、モデル、プロンプトバージョン、処理日時、入力参照、コスト情報を記録する。
- AI出力は事実データと分離し、再生成・比較・監査が可能な状態にする。
- 長時間処理は同期HTTPリクエストから分離し、再試行可能なジョブとして扱う。

## ホスティングと非同期処理

- Next.jsの配信先は当面Vercelとする。
- Vercel固有APIは必要な箇所に限定し、通常のNode.js実行環境でも動かせる構成を優先する。
- 長時間AI処理、大量CSV、バッチ処理はCloud Run等のWorkerへ分離する。
- Workerとの連携はジョブIDと状態遷移をDBに残し、特定キュー製品だけを正としない。
- 外部サービスの障害時に、処理の再実行と状態復旧ができるようにする。

## 禁止事項

- UIコンポーネントからSupabase、OpenAI、Storageを無秩序に直接呼び出す。
- 管理画面だけで本番DB構造を変更し、SQLをGitへ残さない。
- ベンダー固有IDだけを業務上の識別子として利用する。
- AI出力で顧客・商談の原本データを上書きする。
- Secret keyを`NEXT_PUBLIC_`環境変数へ設定する。
- RLSを無効にしてアプリ側の条件指定だけでテナントを分離する。
- 外部サービスの成功応答だけを記録し、ジョブ状態や失敗理由を残さない。

## 例外の扱い

ベンダー固有機能を採用する場合は、次を記録する。

1. 採用する理由
2. 依存する機能とデータ
3. 交換対象となるコード範囲
4. 移行方法または許容するロックイン
5. 再検討する条件

重要な判断はArchitecture Decision Record（ADR）として`docs/adr`へ残す。

## 現在の採用サービス

| 領域 | 現在の採用 | 交換候補 | 依存を閉じ込める場所 |
|---|---|---|---|
| Web | Next.js / Vercel | Cloud Run等 | デプロイ設定、Runtime Adapter |
| DB | Supabase PostgreSQL | Neon、Cloud SQL、RDS | Repository、SQLマイグレーション |
| 認証 | Supabase Auth | Firebase Auth、Auth0 | Auth Adapter、権限判定関数 |
| ファイル | 未確定 | GCS、S3、Supabase Storage | Storage Provider |
| AI | OpenAI予定 | Gemini、Anthropic等 | AI Provider |
| 長時間処理 | Cloud Run予定 | 他のWorker基盤 | Job Runner |

## レビュー時の確認事項

- 新しい外部サービス依存がUIや業務ロジックへ漏れていないか
- データを標準形式で取り出せるか
- 別会社のデータへアクセスできないか
- 認証プロバイダーを変えても業務テーブルを維持できるか
- AIモデルを変更しても分析履歴を維持できるか
- 障害・タイムアウト後に処理を再開できるか
